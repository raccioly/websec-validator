# Glossary

Terms used across the websec-validator documentation, with a pointer to the page that explains each one in
full. Where a term names a field or a file, the spelling here is the spelling that the code uses.

| Term | Definition | Explained in |
|---|---|---|
| **Acknowledgement** | A `fingerprint:<id> # reason` line in `.websec-ignore`. It keeps a known finding visible but excludes it from the gate. A reason is required. An optional `expires:YYYY-MM-DD` makes it lapse. Expired, malformed or reasonless acknowledgements excuse nothing. In SARIF the finding stays, marked suppressed | [Triage and suppression](guides/triage-and-suppression.md) |
| **Agent briefing** | `AGENT-BRIEFING.md`, the main output. It gives your AI agent its orders and covers the detected surface, access-control map, targeting, findings, predicted DAST alerts, staged probes and a phased runbook | [Outputs](reference/outputs.md#agent-briefingmd) |
| **Attack class** | The vulnerability type of a finding (`ssrf`, `missing-auth`, `bola`, `mass-assignment` …). It keys standards citations, calibration buckets, DAST predictions and disposition. `websec explain --list` prints every class this build cites | [CLI reference](reference/cli.md) |
| **Baseline** | A prior `findings-ledger.json` that you pass with `--baseline`. The run classifies each finding as new, unchanged, changed, reopened or no longer observed. New, changed and reopened findings count toward the gate. "No longer observed" does not prove a repair | [Triage and suppression](guides/triage-and-suppression.md) |
| **Blind spot** | An attack class that a DAST scanner does not find on its own, such as BOLA, missing auth or committed secrets. Briefing §4b lists it with the reason. The tool never scores it from scanner silence | [How it works](concepts/how-it-works.md#aim-the-pentest-instead-of-competing-with-it) |
| **BOLA / IDOR** | Broken Object Level Authorization (OWASP API1), also called Insecure Direct Object Reference. One user reads or changes the object of another user or tenant by changing an identifier. You need two identities to confirm it | [Dynamic testing](guides/dynamic-testing.md) |
| **Calibration overlay** | Your local, per-machine addition to the shipped calibration table, under the user cache directory. Only evidence-backed labels enter it. Operator feedback is a candidate until a human accepts it | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Claimspec** | The interchange format of the Guard family. `websec calibrate --claimspec` exports the calibration table as a claimspec v1 `calibration` document with raw counts, caveats and fallback tiers | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Cluster** | A grouping of findings for display only. It groups findings that share one rule, or secrets removed in the same commit. It appears as `clusters[]` in the ledger and §1a in `REPORT.md`. Totals, gate counts and per-site fingerprints do not change | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Constitution** | `CONSTITUTION.md`: the security invariants of the app as Given/When/Then statements derived from recon. A probe confirms or refutes each one | [METHODOLOGY](METHODOLOGY.md#layer-3c--the-security-constitution) |
| **Coverage manifest** | `coverage.json`: what ran, what was skipped and why, which languages had no analyzer, and digests that bind the run to the detector code and the bytes read. `FACTS.json`, the ledger and the envelope also embed it | [Outputs](reference/outputs.md#coveragejson) |
| **DAST** | Dynamic Application Security Testing: scanning a running app over HTTP (for example ZAP or Nuclei). websec does not run a DAST. It predicts what a DAST will report, and it can ingest a DAST report to calibrate | [How it works](concepts/how-it-works.md#aim-the-pentest-instead-of-competing-with-it) |
| **Disposition** | The third finding axis, `agent-fixable` or `human-required`, from a published per-class policy. It says whether an agent may propose the fix alone. It gates nothing | [METHODOLOGY](METHODOLOGY.md#layer-3d--disposition-the-third-axis) |
| **Dynamic phase** | `websec dynamic`: optional checks that you invoke explicitly against a running test instance you own, such as authenticated cross-tenant reads. Never against production | [Dynamic testing](guides/dynamic-testing.md) |
| **EPSS** | FIRST.org's Exploit Prediction Scoring System: an estimated probability, published daily, that someone will exploit a CVE in the next 30 days. websec joins it from a local cache to prioritize dependency CVEs. It does not change severity | [How it works](concepts/how-it-works.md#prioritization) |
| **Execution complete vs clean** | `coverage.execution_complete` means every requested check ran. It does not mean the code is clean or protected. `protection_complete` is always `false`, and a run with no findings means "nothing matched", not "secure". When source is present but none of it has an analyzer, `coverage.files.no_analyzable_source` is `true` and an empty list means "not checked". `--require-analyzed` turns that into exit `3` | [Languages](reference/languages.md#what-a-clean-run-means-for-your-stack) |
| **Extractor** | One of the 22 deterministic recon modules. Each module answers one question about the repository (routes, auth, sinks, IaC …). Its output goes to `FACTS.json` | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **Fingerprint** | The stable identity of a finding (version 2, with version 1 kept as migration aliases). Acknowledgements, baselines, SARIF `partialFingerprints` and `websec feedback` use it | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Fixture scoping** | The default handling of test, example and fixture code. Their routes move to `routes.fixture_endpoints` and the tool does not probe them. Their secrets drop to LOW but stay. Their manifests do not drive framework detection. `--include-fixtures` turns it off | [Triage and suppression](guides/triage-and-suppression.md) |
| **Gate** | The pass/fail decision behind the exit code. The ledger's `gate` block records it: threshold, verdict, failure kind and exit-code contract. `--fail-on`, `--require-complete` and `--require-analyzed` configure it. `websec gate` is a fast, scoped variant for the edit loop | [CLI reference](reference/cli.md) |
| **Guard family** | Three tools that each keep one kind of claim honest. DocGuard checks documentation against code. TestGuard checks tests against what they assert. websec-validator checks security findings against evidence | [README](../README.md) |
| **KEV** | CISA's Known Exploited Vulnerabilities catalog. A CVE on it has reported exploitation in the wild. websec flags it from a local cache | [How it works](concepts/how-it-works.md#prioritization) |
| **Ledger** | `findings-ledger.json`: every finding with its evidence chain, standards citation, remediation, fingerprint, calibrated `P(real)` and disposition, plus the gate record | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Mass assignment** | Binding request fields straight onto a model, so a caller can set fields that they should not, such as `role` or `isAdmin` (OWASP API3, BOPLA). websec extracts the privileged fields of each app to aim the probe | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **MCP** | Model Context Protocol. `websec mcp` exposes typed recon tools over stdio (or loopback HTTP with a token), so MCP clients can call websec directly | [MCP server](reference/mcp.md) |
| **Named profile** | A bounded set of direct-syntax or explicit-configuration checks for one language family, such as `java-spring` or `ios`. A result with no match is not whole-language coverage. `websec capabilities` prints the catalog | [Languages](reference/languages.md#tier-2-and-3-named-check-profiles) |
| **P(real)** | The calibrated probability that a finding is a real vulnerability. The tool measures it per attack class and confidence on a labeled corpus, with a 95% Wilson interval and sample size `n`. It skews optimistic for production code. The interval is the headline | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Probe** | A draft test script staged in `probes/` for this app (BOLA, JWT, SSRF, mass assignment …), with `probe-context.json`. The agent finalizes it, and you run it against a test instance. `websec run` never executes probes | [Outputs](reference/outputs.md#probes) |
| **Reachability (imported vs declared-only)** | A label for a dependency CVE. `imported` means first-party source imports the package. `declared-only` means the package is only declared (likely unreachable; verify). `n/a` means the ecosystem's imports are not parsed. The label is name-based, not a call graph | [How it works](concepts/how-it-works.md#prioritization) |
| **Recon** | The deterministic static pass. It walks the repository once and runs the extractors. It needs only the code | [How it works](concepts/how-it-works.md#the-two-halves) |
| **Route candidate** | A possible endpoint that route discovery could not resolve, for example a Django `include` with a dynamic prefix. The tool keeps it in `coverage.route_discovery` for review and does not promote it to a route | [Languages](reference/languages.md#route-discovery) |
| **Run directory** | `websec-out/runs/<timestamp>-<random>/`. Each attempt gets one, and the tool never overwrites it. `websec-out/latest` points at the most recent completed run | [Outputs](reference/outputs.md#where-artifacts-land) |
| **SARIF** | Static Analysis Results Interchange Format (OASIS, version 2.1.0). Every run writes `results.sarif` for GitHub Code Scanning and other consumers. `--sarif` imports reports from other analyzers | [Outputs](reference/outputs.md#resultssarif) |
| **SBOM** | Software Bill of Materials, the dependency inventory. `--sbom` asks Trivy for CycloneDX (`sbom.cdx.json`) or, with `--sbom spdx`, SPDX (`sbom.spdx.json`) | [Outputs](reference/outputs.md#sbomcdxjson-and-sbomspdxjson) |
| **Service boundary** | The nearest directory that holds a manifest (`package.json`, `go.mod`, `pom.xml` …). The tool groups named profiles, routes and datastores per service. It approximates a deployment boundary and does not prove one | [Languages](reference/languages.md#tier-2-and-3-named-check-profiles) |
| **Sink class** | A category of dangerous operation that user input can reach. The `surface` extractor maps 17 of them, including SQL injection, command injection, SSRF, path traversal, XSS and log injection | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **SSRF** | Server-Side Request Forgery. The server fetches a URL that an attacker controls and so reaches internal services or cloud metadata. websec flags request-derived URLs that reach outbound HTTP calls, including redirects that the code follows without a per-hop check | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **Tenant boundary** | The field that isolates the data of one customer from the data of another (`groupId`, `orgId`, `tenantId` …). websec ranks candidates. Confirm the real one first, because every cross-tenant probe depends on it | [METHODOLOGY](METHODOLOGY.md#layer-1--recon-the-22-extractors) |
| **Thin language coverage** | A coverage gap for languages whose files the tool read but which have no injection, secret or authorization rules, only configuration checks (for example Swift or Rust) | [Languages](reference/languages.md#support-tiers-at-a-glance) |
| **Wilson interval** | The Wilson score confidence interval for a binomial proportion. websec uses its 95% form for `P(real)` because it gives sensible results at small sample sizes | [How it works](concepts/how-it-works.md#calibrated-confidence) |
