# Glossary

Terms used across the websec-validator documentation, with a pointer to where each is explained in
full. Where a term names a field or a file, the spelling here is the one the code uses.

| Term | Definition | Explained in |
|---|---|---|
| **Acknowledgement** | A `fingerprint:<id> # reason` line in `.websec-ignore` that keeps a known finding visible but excludes it from the gate. A reason is required; an optional `expires:YYYY-MM-DD` makes it lapse. Expired, malformed or reasonless acknowledgements excuse nothing. In SARIF the finding stays, marked suppressed | [Triage and suppression](guides/triage-and-suppression.md) |
| **Agent briefing** | `AGENT-BRIEFING.md`, the main output: marching orders for your AI agent covering the detected surface, access-control map, targeting, findings, predicted DAST alerts, staged probes and a phased runbook | [Outputs](reference/outputs.md#agent-briefingmd) |
| **Attack class** | The finding's vulnerability type (`ssrf`, `missing-auth`, `bola`, `mass-assignment` …). It keys standards citations, calibration buckets, DAST predictions and disposition. `websec explain --list` prints every class this build cites | [CLI reference](reference/cli.md) |
| **Baseline** | A prior `findings-ledger.json` passed with `--baseline`. Findings are classified new, unchanged, changed, reopened or no longer observed; new, changed and reopened ones count toward the gate. "No longer observed" does not prove a repair | [Triage and suppression](guides/triage-and-suppression.md) |
| **Blind spot** | An attack class a DAST scanner will not find on its own, such as BOLA, missing auth or committed secrets. Listed in briefing §4b with the reason, and never scored from scanner silence | [How it works](concepts/how-it-works.md#aim-the-pentest-instead-of-competing-with-it) |
| **BOLA / IDOR** | Broken Object Level Authorization (OWASP API1), also called Insecure Direct Object Reference: one user reads or changes another user's or tenant's object by changing an identifier. Needs two identities to confirm | [Dynamic testing](guides/dynamic-testing.md) |
| **Calibration overlay** | Your local, per-machine addition to the shipped calibration table, under the user cache directory. Only evidence-backed labels enter it; operator feedback is a candidate until a human accepts it | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Claimspec** | The Guard-family interchange format. `websec calibrate --claimspec` exports the calibration table as a claimspec v1 `calibration` document with raw counts, caveats and fallback tiers | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Cluster** | A presentation-only grouping of findings that share one rule, or secrets removed in the same commit. Shown as `clusters[]` in the ledger and §1a in `REPORT.md`; totals, gate counts and per-site fingerprints are unchanged | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Constitution** | `CONSTITUTION.md`: the app's security invariants as Given/When/Then statements derived from recon, each confirmed or refuted with a probe | [METHODOLOGY](METHODOLOGY.md#layer-3c--the-security-constitution) |
| **Coverage manifest** | `coverage.json`: what ran, what was skipped and why, which languages had no analyzer, and digests binding the run to the detector code and the bytes read. Also embedded in `FACTS.json`, the ledger and the envelope | [Outputs](reference/outputs.md#coveragejson) |
| **DAST** | Dynamic Application Security Testing: scanning a running app over HTTP (for example ZAP or Nuclei). websec does not run a DAST; it predicts what one will report and can ingest a DAST report to calibrate | [How it works](concepts/how-it-works.md#aim-the-pentest-instead-of-competing-with-it) |
| **Disposition** | The third finding axis, `agent-fixable` or `human-required`, from a published per-class policy. It says whether an agent may propose the fix alone; it gates nothing | [METHODOLOGY](METHODOLOGY.md#layer-3d--disposition-the-third-axis) |
| **Dynamic phase** | `websec dynamic`: optional, explicitly invoked checks against a running TEST instance you own, such as authenticated cross-tenant reads. Never against production | [Dynamic testing](guides/dynamic-testing.md) |
| **EPSS** | FIRST.org's Exploit Prediction Scoring System: an estimated probability, published daily, that a CVE will be exploited in the next 30 days. websec joins it from a local cache to prioritize dependency CVEs, without changing severity | [How it works](concepts/how-it-works.md#prioritization) |
| **Execution complete vs clean** | `coverage.execution_complete` means every requested check ran. It does not mean the code is clean or protected: `protection_complete` is always `false`, and a run with no findings is "nothing matched", not "secure". When source is present but none of it has an analyzer, `coverage.files.no_analyzable_source` is `true` and an empty list means "not checked"; `--require-analyzed` turns that into exit `3` | [Languages](reference/languages.md#what-a-clean-run-means-for-your-stack) |
| **Extractor** | One of the 22 deterministic recon modules, each answering one question about the repository (routes, auth, sinks, IaC …). Output lands in `FACTS.json` | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **Fingerprint** | The stable identity of a finding (version 2, with version 1 kept as migration aliases). Used by acknowledgements, baselines, SARIF `partialFingerprints` and `websec feedback` | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Fixture scoping** | Default handling of test, example and fixture code: their routes move to `routes.fixture_endpoints` and are not probed, their secrets are demoted to LOW but kept, and their manifests do not drive framework detection. `--include-fixtures` turns it off | [Triage and suppression](guides/triage-and-suppression.md) |
| **Gate** | The pass/fail decision behind the exit code, recorded in the ledger's `gate` block: threshold, verdict, failure kind and exit-code contract. `--fail-on`, `--require-complete` and `--require-analyzed` configure it; `websec gate` is a fast scoped variant for the edit loop | [CLI reference](reference/cli.md) |
| **Guard family** | Three tools that each keep one kind of claim honest: DocGuard (documentation against code), TestGuard (tests against what they assert) and websec-validator (security findings against evidence) | [README](../README.md) |
| **KEV** | CISA's Known Exploited Vulnerabilities catalog. A CVE on it has reported exploitation in the wild; websec flags it from a local cache | [How it works](concepts/how-it-works.md#prioritization) |
| **Ledger** | `findings-ledger.json`: every finding with evidence chain, standards citation, remediation, fingerprint, calibrated `P(real)` and disposition, plus the gate record | [Outputs](reference/outputs.md#findings-ledgerjson) |
| **Mass assignment** | Binding request fields straight onto a model so a caller can set fields they should not, such as `role` or `isAdmin` (OWASP API3, BOPLA). websec extracts each app's privileged fields to aim the probe | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **MCP** | Model Context Protocol. `websec mcp` exposes typed recon tools over stdio (or loopback HTTP with a token) so MCP clients can call websec directly | [MCP server](reference/mcp.md) |
| **Named profile** | A bounded set of direct-syntax or explicit-configuration checks for one language family, such as `java-spring` or `ios`. A no-match result is not whole-language coverage. `websec capabilities` prints the catalog | [Languages](reference/languages.md#tier-2-and-3-named-check-profiles) |
| **P(real)** | The calibrated probability that a finding is a real vulnerability, measured per attack class and confidence on a labeled corpus, with a 95% Wilson interval and sample size `n`. Skews optimistic for production code; the interval is the headline | [How it works](concepts/how-it-works.md#calibrated-confidence) |
| **Probe** | A draft test script staged in `probes/` for this app (BOLA, JWT, SSRF, mass assignment …), with `probe-context.json`. The agent finalizes it; you run it against a TEST instance. `websec run` never executes probes | [Outputs](reference/outputs.md#probes) |
| **Reachability (imported vs declared-only)** | For a dependency CVE: `imported` if first-party source imports the package, `declared-only` if it is only declared (likely unreachable; verify), `n/a` for ecosystems whose imports are not parsed. Name-based, not a call graph | [How it works](concepts/how-it-works.md#prioritization) |
| **Recon** | The deterministic static pass: walk the repository once and run the extractors. Needs only the code | [How it works](concepts/how-it-works.md#the-two-halves) |
| **Route candidate** | A possible endpoint that route discovery could not resolve, for example a Django `include` with a dynamic prefix. Kept in `coverage.route_discovery` for review instead of being promoted to a route | [Languages](reference/languages.md#route-discovery) |
| **Run directory** | `websec-out/runs/<timestamp>-<random>/`, one per attempt and never overwritten. `websec-out/latest` points at the most recent completed run | [Outputs](reference/outputs.md#where-artifacts-land) |
| **SARIF** | Static Analysis Results Interchange Format (OASIS, version 2.1.0). `results.sarif` is written on every run for GitHub Code Scanning and other consumers; `--sarif` imports reports from other analyzers | [Outputs](reference/outputs.md#resultssarif) |
| **SBOM** | Software Bill of Materials: the dependency inventory. `--sbom` asks Trivy for CycloneDX (`sbom.cdx.json`) or, with `--sbom spdx`, SPDX (`sbom.spdx.json`) | [Outputs](reference/outputs.md#sbomcdxjson-and-sbomspdxjson) |
| **Service boundary** | The nearest directory holding a manifest (`package.json`, `go.mod`, `pom.xml` …). Named profiles, routes and datastores are grouped per service. It approximates, and does not prove, a deployment boundary | [Languages](reference/languages.md#tier-2-and-3-named-check-profiles) |
| **Sink class** | A category of dangerous operation that user input can reach. The `surface` extractor maps 17, including SQL injection, command injection, SSRF, path traversal, XSS and log injection | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **SSRF** | Server-Side Request Forgery: the server fetches a URL an attacker controls, reaching internal services or cloud metadata. websec flags request-derived URLs reaching outbound HTTP calls, including redirects followed without a per-hop check | [How it works](concepts/how-it-works.md#what-it-extracts) |
| **Tenant boundary** | The field that isolates one customer's data from another's (`groupId`, `orgId`, `tenantId` …). websec ranks candidates; you confirm the real one first, because every cross-tenant probe depends on it | [METHODOLOGY](METHODOLOGY.md#layer-1--recon-the-22-extractors) |
| **Thin language coverage** | A coverage gap for languages whose files were read but which have no injection, secret or authorization rules, only configuration checks (for example Swift or Rust) | [Languages](reference/languages.md#support-tiers-at-a-glance) |
| **Wilson interval** | The Wilson score confidence interval for a binomial proportion. websec uses its 95% form for `P(real)` because it stays sensible at small sample sizes | [How it works](concepts/how-it-works.md#calibrated-confidence) |
